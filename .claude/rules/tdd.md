# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"로 처리하지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트별 규칙이 다루지 않는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- 비즈니스 로직
- API (핸들러, 요청/응답 처리, 외부 호출 래퍼)
- 유틸리티 / 순수 함수
- **버그 수정** (재현 테스트를 먼저 작성해 실패를 확인한 뒤 수정)
- 동작이 있는 훅, 상태 로직

### TDD 불필요

- 타입 정의 (`type`, `interface` 선언)
- 설정 파일 (tsconfig, vite/eslint 설정, package.json 등)
- 순수 UI (스타일링, 레이아웃, 정적 마크업)
- SQL / 마이그레이션 스크립트

경계가 모호하면 **TDD를 적용**한다.

## RED-GREEN-REFACTOR

### 1. RED

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트만 먼저 작성한다. 프로덕션 코드는 건드리지 않는다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류, 잘못된 셋업으로 인한 실패는 RED가 아니다. 테스트를 고쳐 올바른 이유로 실패시킨다.

### 2. GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 현재 테스트가 요구하지 않는 분기, 옵션, 추상화는 넣지 않는다.
- **신규 테스트와 기존 테스트 모두** 실행해 통과를 확인한다.

### 3. REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **모든 테스트가 green인 상태를 유지**한다. 변경마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 4. 반복

다음 동작에 대해 **RED로 돌아간다.** 모든 요구 동작이 테스트로 커버될 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 포함한다. 삭제는 삭제다.
- 테스트를 먼저 쓰고 나서 그 코드를 새로 작성한다. 복사하지 않는다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 단순한 코드에서 나는 버그가 가장 늦게 발견된다. |
| 나중에 추가하겠다 | 나중에 쓴 테스트는 이미 통과하는 코드에 맞춘 것이라 실패를 검증하지 못한다. 실제로 "나중"은 오지 않는다. |
| 시간이 없다 | 디버깅과 회귀 수정이 테스트 작성보다 오래 걸린다. 시간이 없을수록 RED로 범위를 좁히는 것이 빠르다. |
| 삭제하면 낭비 | 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. 삭제하고 다시 시작한다. |
| 프로토타입이다 | 프로토타입은 프로덕션이 된다. 버릴 코드라면 이 규칙의 적용 대상이 아니라고 사용자가 명시적으로 선언해야 한다. 에이전트가 단독으로 판단하지 않는다. |
