# commit

변경사항을 분석하여 컨벤션에 맞는 한국어 커밋 메시지로 커밋한다.

## 절차

### 1. 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 스타일 참고 (커밋이 없으면 생략)
```

- untracked 파일은 내용을 직접 읽어 성격을 파악한다.
- 비밀 정보(`.env`, 키, 토큰, 자격증명)나 빌드 산출물(`node_modules`, `dist` 등)이 포함돼 있으면 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다 (기능 추가, 버그 수정, 리팩터링, 설정 변경을 섞지 않는다).
- 파일 단위로 나누기 어려우면 `git add -p` 대신 변경 성격별로 파일을 묶는다.
- 변경이 단일 목적이면 커밋 1개로 충분하다. 억지로 쪼개지 않는다.
- 초기 커밋처럼 untracked 파일이 대량이면 성격별(설정/소스/서버/문서 등)로 묶는다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택): 무엇을, 왜 바꿨는지>
```

| type | 용도 |
| --- | --- |
| feat | 새로운 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 빌드·설정·의존성·기타 잡무 |

- 요약은 한국어, 50자 이내, 마침표 없이 명사형/간결체로 쓴다. (예: `feat: 컴포넌트 생성 API 추가`)
- 본문은 "왜"가 자명하지 않을 때만 추가한다.
- 위 4개에 맞지 않는 변경(문서, 테스트, 스타일 등)은 가장 가까운 type을 쓰되, 프로젝트 기존 로그가 `docs`/`test` 등을 쓰고 있으면 그것을 따른다.
- 시스템 지시에 커밋 메시지 끝에 붙일 attribution 문구가 있으면 그대로 마지막에 추가한다.

### 4. 바로 커밋

**승인을 기다리지 않고 즉시 커밋한다.** 커밋 전에 질문하지 않는다. 사용자가 `--confirm`, "확인받고 커밋" 등을 요청한 경우에만 커밋별 파일 목록과 메시지를 보여주고 승인을 받는다.

```bash
git add <파일들>          # 파일을 명시. `git add -A`/`.` 는 의도한 전체일 때만
git commit -m "<메시지>"   # 여러 줄은 heredoc 사용
git status --short        # 결과 확인
```

- 커밋이 여러 개면 순서대로 add → commit을 반복한다.
- pre-commit hook 실패 시 `--no-verify`로 우회하지 말고 원인을 고친 뒤 **새 커밋**을 만든다.
- 완료 후 생성된 커밋 해시, 메시지, 포함 파일을 요약해서 보고한다.

## 금지 사항

- 비밀 정보·빌드 산출물은 자동 커밋하지 않고 제외한 뒤 보고
- `git push`, `--amend`, `reset --hard`, `--force` 등은 명시적 요청이 있을 때만
- 기본 브랜치(main)에 있을 때는 새 브랜치를 만들어 커밋하고 그 사실을 보고
- git config 변경 금지
